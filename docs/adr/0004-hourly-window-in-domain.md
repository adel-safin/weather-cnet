# ADR 0004. Почасовое окно считается в домене по локальному времени локации

Статус: принято

## Контекст

Требование: показать оставшиеся часы текущего дня и все часы следующего. Провайдер отдаёт три календарных дня по 24 часа в местном времени локации. Нужно решить, где и по какому времени выбирать окно.

## Решение

Правило живёт в `Weather.Domain.Forecasts.HourlyWindow` и опирается на локальное время локации, полученное из ответа провайдера. Текущий час включается в окно.

## Причины

- Время сервера не подходит: приложение, развёрнутое во Франкфурте или в контейнере с UTC, показывало бы москвичу неверную границу дня.
- Часовой пояс вычисляется из пары `localtime` и `localtime_epoch`, а не через `TimeZoneInfo.FindSystemTimeZoneById(tz_id)`, — образу не нужна база часовых поясов, и поведение не зависит от операционной системы.
- Правило в домене тестируется без HTTP и без UI: покрыты 23:00, полночь, начало дня и конец следующего.
- Текущий час включён намеренно: пользователь ожидает увидеть слот, в котором находится, а не следующий за ним.

## Последствия

- В UI не остаётся условной логики по датам, компоненты только группируют готовый список.
- Количество часов в ответе меняется в течение суток (от 25 до 48). Тесты фиксируют это как ожидаемое поведение, а не как случайность.
