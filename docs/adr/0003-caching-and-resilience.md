# ADR 0003. Кэш поверх порта и стандартный обработчик устойчивости

Статус: принято

## Контекст

Бесплатный ключ weatherapi.com имеет месячный лимит, а сами данные обновляются примерно раз в 15 минут. Каждое открытие страницы делает два запроса наружу. Сеть периодически даёт временные сбои.

## Решение

- Устойчивость: `AddStandardResilienceHandler()` на типизированном клиенте — повторы, размыкатель цепи, таймаут попытки и общий таймаут. Параметры выведены из `WeatherApiOptions`.
- Кэш: декоратор `CachedWeatherProvider` поверх `IWeatherProvider` на `HybridCache`. TTL: 5 минут для текущей погоды, 15 минут для прогноза. Нулевой TTL полностью отключает кэш.

## Причины

- Декоратор оставляет `WeatherApiClient` занятым только HTTP: кэш можно снять или заменить, не трогая клиент, а вызывающий код вообще не знает о кэшировании.
- `HybridCache` из коробки защищает от cache stampede: при одновременных запросах наружу уходит один.
- Стандартный обработчик из `Microsoft.Extensions.Http.Resilience` вместо ручных политик Polly — меньше кода и разумные значения по умолчанию, проверенные командой .NET.
- Повторяются только временные сбои (5xx, таймауты); 401 и 400 повторять бессмысленно, что подтверждено тестом.

## Последствия

- Доменные снимки проходят через сериализацию кэша, а `Coordinates` создаётся только фабрикой и не имеет публичного конструктора. Поэтому в инфраструктуре живёт `CoordinatesJsonConverter` и явный `IHybridCacheSerializer`; домен не обвешан атрибутами сериализации.
- Данные на экране могут отставать от провайдера на время TTL. Для погоды это незаметно, а кнопка «Обновить» всё равно ограничена тем же кэшем — осознанный размен на экономию лимита.
- Сейчас используется только L1 (память процесса). Подключение L2 (Redis) не потребует правок в коде: достаточно зарегистрировать `IDistributedCache`.
